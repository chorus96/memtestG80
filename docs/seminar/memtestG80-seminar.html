MemtestG80
GPU 메모리를 어떻게 검증하는가

ECC 없는 GPU에서 조용히 발생하는 비트 오류를, 수십만 스레드의 병렬성으로 잡아내는 오픈소스 하드웨어 메모리 테스터의 내부 구조를 코드로 따라 읽습니다.

대상 memtestG80 (Stanford, 2009) 언어 CUDA C++ / LGPL v3 핵심 파일 memtestG80_core.cu
문제 제기

GPU는 조용히 틀린다

  • 소비자용 GPU 대부분은 ECC(오류 정정)가 없다 — 비트가 뒤집혀도 아무도 모른 채 잘못된 값이 계산에 섞인다.
  • 오버클럭·발열·전압 마진 부족은 산발적(intermittent) 오류를 만든다. 평소엔 멀쩡하다가 특정 패턴에서만 실패한다.
  • GPGPU 연산(과학 계산, 렌더링, Folding@home)에서 한 비트의 오염이 결과 전체를 무의미하게 만들 수 있다.
  • CPU용 Memtest86는 있지만, GPU의 VRAM은 CPU에서 직접 두드릴 수 없다 — GPU 위에서 도는 테스터가 필요하다.

사례 실전에서의 신호

README는 말한다: "문제 있는 카드조차 5만 번에 한 번 꼴로만 실패할 수 있다."

그래서 권장 사용법은 가능한 큰 영역을, 수천 번 반복하는 것. 메모리 테스트는 스트레스 테스트다 — 짧게 돌려서는 잡히지 않는다.

한눈에

MemtestG80이란

Stanford의 Folding@home 팀이 만든, Memtest86의 메모리 테스트들을 CUDA 커널로 이식한 도구. 폐쇄형 버전의 오픈소스 에디션이다.

라이브러리 우선

개발자가 자기 코드에 링크해 실행 전 GPU 건전성을 검증하도록 설계. 핵심 API는 memtestG80_core.h.

+ CLI 프런트엔드

memtestG80_cli.cu는 라이브러리 사용 예제이자 독립 실행형 테스터. 13종 테스트를 순차 실행.

이식성

Linux 32/64, macOS, Windows용 Makefile 제공. 인자 파싱은 헤더 전용 ezOptionParser.

1024 × 512기본 그리드 — 블록 × 스레드 = 524,288 스레드
2 MiB그리드당 N=1 word일 때 테스트되는 메모리 단위
배경 지식 · 30초

CUDA 실행 모델, 딱 필요한 만큼

  • 커널(__global__)은 grid 위에서 실행. grid는 block들로, block은 thread들로 구성된다.
  • 각 스레드는 blockIdx.x, threadIdx.x, blockDim.x로 자기 위치를 안다 → 자기가 맡을 메모리 주소를 계산.
  • 메모리 계층: global(VRAM, 테스트 대상) · shared(블록 내 공유, 빠름) · register(스레드 전용).
  • 한 블록의 스레드들은 __syncthreads()로 동기화 가능 → 병렬 리덕션의 열쇠.
// core.cu 상단 주석 — 의도된 사용법 grid = 1024 blocks block = 512 threads // N words(iterations) per thread // 그리드당 테스트 용량: 1024 × 512 × N × 4B = 2·N MiB

MemtestG80은 grid/block/thread를 1차원 선형으로만 쓴다 — 메모리는 결국 1차원 주소 공간이므로.

핵심 메커니즘 ①

스레드 → 주소 매핑

#define THREAD_ADDRESS(base, N, i) \ (base + blockIdx.x * N * blockDim.x + i * blockDim.x + threadIdx.x)

모든 테스트의 심장. 스레드 t가 i번째 반복에 건드릴 word 주소를 계산한다.

  • 인터리빙이 핵심: 같은 반복 i에서 이웃 스레드(threadIdx.x)는 이웃한 주소를 맡는다.
  • 덕분에 워프의 32개 접근이 하나의 트랜잭션으로 묶이는 메모리 coalescing이 일어나 대역폭을 최대로 쓴다.
  • 블록은 N·blockDim.x word씩 널찍이 떨어진 구역을 담당 → 전체 영역을 빈틈없이 덮는다.

핵심 메커니즘 ③ · 가장 영리한 부분

오류를 세는 두 가지 묘수

묘수 1 비트 단위 카운트

단순히 "틀렸다/맞았다"가 아니라, __popc(x ^ constant)로 뒤집힌 비트의 개수를 센다. 한 word에서 여러 비트가 상해도 모두 포착.

묘수 2 병렬 리덕션

스레드별 오류 수를 shared memory에 모으고, stride를 반씩 줄이며 블록 안에서 합산. 블록 합만 호스트로 복사해 CPU가 최종 합(~1k개)을 더한다.

extern __shared__ uint tErr[]; tErr[threadIdx.x] = 0; for (uint i=0; i// BITSDIFF(x,y) = __popc((x)^(y)) // 블록 내 트리 리덕션 for (uint s=blockDim.x>>1; s>0; s>>=1) { __syncthreads(); if (threadIdx.x < s) tErr[threadIdx.x] += tErr[threadIdx.x + s]; } if (threadIdx.x==0) blockErrorCount[blockIdx.x] = tErr[0];

각 walking 테스트는 shift를 8·32번 돌리므로, 실제 커널 실행 횟수는 표의 행 수보다 훨씬 많다.

테스트 심화 ①

Moving Inversions

가장 고전적인 메모리 테스트. 패턴을 쓰고 → 검증 → 보수 패턴으로 덮고 → 다시 검증.

  • ones/zeros: 0xFFFFFFFF를 쓰고 확인한 뒤, 0x0으로 반전해 다시 확인.
  • 모든 셀이 1과 0을 모두 안정적으로 저장하는지, 그리고 이웃이 값을 오염시키지 않는지 검증.
  • random 변형은 상수 대신 난수 패턴을 써서 특정 값에 의존한 결함을 노린다.
gpuWriteConstant (..., 0xFFFFFFFF); err = gpuVerifyConstant(..., 0xFFFFFFFF); gpuWriteConstant (..., 0x0); err += gpuVerifyConstant(..., 0x0); return err; // 두 위상의 오류 합
테스트 심화 ②

Walking Bits

M86 Walking 8-bit

한 비트만 켠 8비트 패턴(1<<shift)을 32비트로 복제해 전 영역에 동일하게 기록·검증하고, 보수도 검증. shift를 0~7 반복.

True Walking 8-bit

워드 안에서 켜진 비트가 실제로 이동하도록 페어 패턴을 구성. 인접 워드 간 데이터·주소 라인 결합 결함에 더 민감.

Walking 32-bit

32비트 전 폭에 걸쳐 단일 비트를 이동시키며(shift 0~31) 각 데이터 라인을 독립적으로 자극.

shift &= 0x7; uint pattern = 1 << shift; pattern = pattern | (pattern<<8) | (pattern<<16) | (pattern<<24); // 8비트를 워드 전체로 복제
테스트 심화 ③

Random Blocks & Modulo-20

#7 Random Blocks

호스트의 rand() 시드로 각 블록에 재현 가능한 난수를 채운다. 쓸 때와 검증할 때 같은 시드로 같은 수열을 재생성해 비교.

구조화된 패턴이 놓치는, 데이터 의존적 결함을 잡는다.

#8 Modulo-20

20개 word마다 한 번씩 패턴을 배치하고 나머지는 보수로 채운 뒤, shift를 0~19로 돌린다.

주기적 주소 간섭 — 특정 간격의 셀들이 서로 영향을 주는 결함을 표적한다.

두 테스트 모두 매 iteration마다 새 rand() 값을 받아 실행마다 다른 데이터로 커버리지를 넓힌다.

테스트 심화 ④ · 메모리가 아니라 연산을 본다

Logic Test — Short LCG

  • 다른 테스트가 저장을 본다면, 이건 ALU와 반복 제어를 본다 — 짧은 주기의 선형합동생성기(LCG)를 k·period번 돌린다.
  • 주기 후 값은 항상 0으로 되돌아오도록 설계 → 결과를 0과 비교. 반복 횟수 k가 달라도 결과는 같아야 하므로, 차이가 나면 로직 오류.
  • 짝 XOR(^0xFFFFFFF0 ^0xF)로 명령 스트림에 다양성을 준다 — 단일 XOR처럼 NOT으로 최적화돼 사라지지 않게(decuda로 검증).
  • shmem 버전은 중간값을 shared memory에 둬서 셰이더 오버클럭발 shared-mem 오류에 더 민감.
for (rep = 0; rep < repeats; rep++) { value = ~value; #pragma unroll 1 for (iter=0; iter// LCG 스텝 value ^= 0xFFFFFFF0; value ^= 0xF; // 짝 XOR } value = ~value; } // 끝나면 value는 0 이어야 정상
부가 기능

메모리 대역폭 측정

테스트 전, 디바이스 내부 device-to-device 복사를 반복해 실효 대역폭을 잰다.

  • D2D cudaMemcpy는 비동기라 cudaThreadSynchronize()로 반드시 동기화 후 시간을 재야 정확.
  • 읽기 + 쓰기 둘 다 일어나므로 대역폭에 ×2를 곱한다.
  • 기대치보다 크게 낮으면 그 자체가 하드웨어/드라이버 이상 신호.
for (i=0; icudaMemcpy(dst, src, bytes, D2D); cudaThreadSynchronize(); // 정확한 타이밍 // 읽고 쓰므로 ×2 bw = 2.0 * mbToTest*iters / seconds;

실전

돌리는 법 · 읽는 법

# 기본: GPU 0, 128MB, 50 iters memtestG80 # 256MB를 100회, 3번째 GPU에서 memtestG80 --gpu 2 256 100
  • 테스트 영역은 2MB 단위로 반올림. VRAM 전부는 못 쓴다(OS 예약분).
  • 종료 코드는 누적 오류 수가 0이 아니면 non-zero → 스크립트 연동 쉬움.

해석 40억 개 오류?

디스플레이를 구동 중인 GPU는 드라이버 워치독 타임아웃이 걸릴 수 있다. 오류 수가 40억을 넘으면 실제 결함이 아니라 타임아웃 — 영역을 줄이면 사라진다.

원칙 오래, 크게

안정성 검증은 스트레스 테스트다. 의심되면 가능한 큰 영역을 수천 회 — 산발적 결함은 그래야 드러난다.

정리

핵심 세 가지

01

검증된 알고리즘의 병렬 이식. Memtest86의 시간 검증된 테스트들을, 수십만 스레드로 VRAM을 동시에 두드리도록 CUDA로 옮겼다.

02

단순한 원리, 영리한 디테일. "쓰고 되읽기"라는 뼈대 위에, __popc 비트 카운트와 병렬 리덕션이 성능과 정확도를 만든다.

03

메모리 + 로직 둘 다. 저장뿐 아니라 LCG로 ALU·반복 제어까지 시험 — 오버클럭 안정성 검증에 유효하다.

읽을 순서 제안: memtestG80_cli.cu의 메인 루프 → core.cu의 THREAD_ADDRESS → deviceVerifyConstant의 리덕션. 이 세 곳이 전체를 관통한다.
