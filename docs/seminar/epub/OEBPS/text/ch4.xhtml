4. 테스트 카탈로그 · API · 결론

4.1 13종 테스트 카탈로그

메인 루프(memtestG80_cli.cu:185)는 한 번의 반복(iteration)마다 13종의 테스트를 순서대로 실행합니다. 테스트마다 다른 것은 "패턴 생성" 뿐이며, 2·3장에서 본 쓰기·검증·리덕션 뼈대는 그대로 재사용됩니다.

표 3. 테스트 카탈로그와 Memtest86 계보
테스트계보노리는 결함
Moving Inversions (1/0)Memtest86 #2stuck bit · 인접 간섭
Walking 8-bit (M86)Memtest86 #3데이터 라인 단락

Walking 32-bit (0/1)Memtest86 #6전체 워드폭 데이터 라인

Modulo-20Memtest86 #8주기적 주소 간섭
Logic / Short LCG (+shmem)고유연산 로직 · 반복 카운트

패턴은 비트 연산만으로 생성됩니다. 예를 들어 Walking 8-bit는 한 비트만 켠 값을 워드 전체로 복제합니다.

특기할 만한 것은 Logic 테스트입니다. 다른 테스트가 메모리 저장을 검사한다면, 이 테스트는 ALU와 반복 제어를 검사합니다. 짧은 주기의 선형합동생성기(LCG, Linear Congruential Generator)를 k·period번 돌리되, 주기 후 값이 항상 0으로 되돌아오도록 설계합니다. 반복 횟수 k가 달라도 결과가 같아야 하므로, 차이가 나면 그것은 메모리가 아니라 로직 오류입니다. 오버클럭 안정성 검증에 특히 유용합니다.

4.2 대역폭 측정

테스트 전, 디바이스 내부의 device-to-device 복사를 반복해 실효 대역폭을 잽니다.

4.3 3계층 API 설계

MemtestG80의 코드는 세 계층으로 깔끔하게 나뉩니다.

  • Layer 3 · memtestState 클래스 — 사용자에게 권장되는 객체지향 인터페이스. allocate()가 자원을 잡고, 각 gpuXxx() 메서드가 성공/실패를 bool로 반환합니다.
  • Layer 2 · __host__ gpuXxx 함수 — 커널 실행 + 동기화 + 오류 리덕션을 묶은 저수준 C API.
  • Layer 1 · __global__ deviceXxx 커널 — GPU에서 실제로 도는 테스트 본체. 내부 전용입니다.

memtestState는 C++의 RAII(Resource Acquisition Is Initialization) 패턴을 GPU 자원에 적용합니다. 소멸자가 deallocate()를 호출하므로, 객체가 스코프를 벗어나면 GPU 메모리가 자동 해제되어 누수를 막습니다. 이 도구를 라이브러리로 임베드하는 것은 다음처럼 간단합니다.

오류 센티넬 — 40억을 넘는 "오류"의 정체

반환값이 0xFFFFFFFF이면 커널 실행 실패, 0xFFFFFFFE이면 타임아웃입니다. 즉, 오류 수가 40억을 넘게 나오면 이는 진짜 결함이 아니라 센티넬 값이며, 대개 디스플레이를 구동 중인 GPU의 드라이버 워치독 타임아웃입니다. 테스트 영역을 줄이면 사라집니다.

4.4 결론

MemtestG80은 "GPU 메모리에 값을 쓰고, 다시 읽어 비교한다"는 단순한 아이디어를, 검증된 Memtest86 알고리즘과 CUDA의 병렬성으로 구현한 도구입니다. 그 안에는 입문자가 배울 수 있는 CUDA의 정수가 모두 담겨 있습니다 — THREAD_ADDRESS의 스레드 주소 매핑과 메모리 병합, __popc와 공유 메모리 트리 리덕션, 그리고 RAII 기반의 3계층 API 설계입니다.

코드를 처음 읽는다면 다음 순서를 권합니다.

  1. memtestG80_cli.cu의 메인 루프 — 전체 흐름을 조망
  2. memtestG80_core.cu:26의 THREAD_ADDRESS — 모든 테스트의 심장
  3. memtestG80_core.cu:213의 deviceVerifyConstant — 병렬 리덕션

이 세 곳이 MemtestG80 전체를 관통합니다.
