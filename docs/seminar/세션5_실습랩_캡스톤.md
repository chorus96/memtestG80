## 오늘의 주인공 코드 — 3계층의 꼭대기

```c
// memtestG80_core.h:65 — memtestState 클래스 (LAYER 3)
class memtestState {
    const uint nBlocks;      // 1024
    const uint nThreads;     // 512
    uint* devTestMem;        // 테스트 대상 전역 메모리
    ...
public:
    uint allocate(uint mbToTest);        // 자원 확보 (실패 시 0)
    void deallocate();                   // 해제
    bool gpuMovingInversionsOnesZeros(uint& errorCount) const;   // 성공/실패 bool
    ...
    ~memtestState() { deallocate(); }    // 소멸자가 자동 정리 (RAII)
};
```

- **LAYER 3** `memtestState` (사용자 권장) → **LAYER 2** `__host__ gpuXxx` → **LAYER 1** `__global__ deviceXxx`

## Exercise 1 — 최소 임베드 프로그램 작성

**① 목표**: `memtestState`를 내 프로그램에서 직접 써서 GPU를 검증한다.

**② 코드**: 저장소 루트에 `health.cu`를 새로 만듭니다.

```c
// health.cu
#include <stdio.h>
#include "memtestG80_core.h"

int main() {
    memtestState tester;
    if (!tester.allocate(64)) {                 // 64MB 확보
        printf("allocate 실패\n");
        return 2;
    }
    uint errors = 0, e = 0;
    tester.gpuMovingInversionsOnesZeros(e); errors += e;
    for (uint s = 0; s < 8; s++) { tester.gpuWalking8BitM86(e, s); errors += e; }

    printf("총 오류: %u → GPU %s\n", errors, errors == 0 ? "건강함" : "의심됨");
    return errors != 0;                          // 소멸자가 메모리 자동 해제
}
```

**③ 빌드/실행**:
```bash
nvcc -DLINUX -O2 -m64 -o health memtestG80_core.o health.cu    # core.o는 make로 이미 생성됨
./health
```

> `memtestG80_core.o`가 없다면 먼저 `make -f Makefiles/Makefile.linux64`로 만드세요.

**④ 관찰**: "GPU 건강함"이 출력되나요? 종료 코드(`echo $?`)가 0인지 확인.

**⑤ 생각해보기**: `main`이 끝날 때 `tester`의 소멸자가 호출되어 GPU 메모리가 해제됩니다. `cudaFree`를 직접 부르지 않아도 되는 이유는(RAII)?

## Exercise 2 — allocate 실패 다루기

**① 목표**: 자원 확보 실패가 안전하게 처리되는지 본다.

**② 코드**: `health.cu`에서 비현실적으로 큰 크기를 요청합니다.

```c
    if (!tester.allocate(1000000)) {            // 1TB 요청 → 실패
        printf("allocate 실패 (예상된 동작)\n");
        return 2;
    }
```

**③ 실행**:
```bash
nvcc -DLINUX -O2 -m64 -o health memtestG80_core.o health.cu
./health
```

**④ 관찰**: 크래시 없이 "실패"가 깔끔하게 출력되나요? `allocate`(core.cu:51)의 `try/throw`가 부분 할당을 되돌립니다.

**⑤ 생각해보기**: `allocate`는 3번의 할당 중 하나라도 실패하면 이미 잡은 것을 `cudaFree`하고 0을 반환합니다. 이런 "예외 안전"이 왜 중요한가요?

> **끝나면 원복**: 크기를 다시 64로.

## Exercise 3 — 오류 센티넬 직접 만나기

**① 목표**: 4억을 넘는 "오류"의 정체(타임아웃 센티넬)를 확인한다.

**② 코드**: `SOFTWAIT`의 타임아웃 한계를 아주 짧게 만들어 타임아웃을 유발합니다.
`memtestG80_core.h:49` 부근:

```c
// #define SOFTWAIT() if (_pollStatus() != 0) {return 0xFFFFFFFE;}
#define SOFTWAIT() if (_pollStatus(1, 1) != 0) {return 0xFFFFFFFE;}   // limit=1ms (거의 즉시 타임아웃)
```

**③ 실행**:
```bash
make -f Makefiles/Makefile.linux64
./memtestG80 512 1               # 큰 영역 → 커널이 1ms 안에 못 끝남
```

**④ 관찰**: 오류 수가 `0xFFFFFFFE`(= 4,294,967,294)처럼 **40억대**로 나오나요? 이것이 진짜 오류가 아니라 센티넬입니다.

**⑤ 생각해보기**: `memtestState`의 `gpuXxx` 메서드(core.cu:102 등)는 이 센티넬을 걸러 `bool false`로 바꿉니다. uint 반환값에 특수값을 얹는 관례의 장단점은?

> **반드시 원복**: `SOFTWAIT` 매크로를 원래대로.

### (A) 새 패턴 테스트 — 체커보드 ★기본
세션 1~3의 뼈대를 그대로 재사용해 새 테스트를 추가합니다.

1. `memtestG80_core.h`에 선언 추가:
   ```c
   bool gpuCheckerboard(uint& errorCount) const;
   ```
2. `memtestG80_core.cu`에 구현 — Moving Inversions를 본떠 `0xAAAAAAAA`/`0x55555555` 사용:
   ```c
   bool memtestState::gpuCheckerboard(uint& errorCount) const {
       if (!allocated) return false;
       gpuWriteConstant(nBlocks,nThreads,devTestMem,loopIters,0xAAAAAAAA);
       SOFTWAIT();
       errorCount  = gpuVerifyConstant(nBlocks,nThreads,devTestMem,loopIters,0xAAAAAAAA,devTempMem,hostTempMem);
       gpuWriteConstant(nBlocks,nThreads,devTestMem,loopIters,0x55555555);
       SOFTWAIT();
       errorCount += gpuVerifyConstant(nBlocks,nThreads,devTestMem,loopIters,0x55555555,devTempMem,hostTempMem);
       return cudaGetLastError() == cudaSuccess;
   }
   ```
3. `memtestG80_cli.cu`의 메인 루프에 호출 한 줄 추가, 오류 수 출력.

**발표 포인트**: 뼈대 재사용으로 새 테스트가 얼마나 적은 코드로 되는가.

### (B) 오류 히스토그램 — 세션 3 응용
`deviceVerifyConstant`의 리덕션을 응용해, 오류가 난 **비트 위치**별 빈도를 집계하는 진단 기능을 추가합니다.
- 힌트: `__popc` 대신, XOR 결과의 각 비트를 32칸 히스토그램(공유 배열)에 누적한 뒤 리덕션.

**발표 포인트**: 특정 비트 위치에 오류가 몰리면 무엇을 의미하는가(데이터 라인 결함).

### (C) 선택적 테스트 실행 — 세션 4·5 구조
`ezOptionParser`를 이용해 CLI에 `--only <name>` 플래그를 추가, 특정 테스트만 돌리도록 확장합니다.
- 힌트: `memtestG80_cli.cu:83`의 `opt.add(...)` 패턴을 따라 새 플래그 등록.

**발표 포인트**: 3계층 구조 덕에 CLI만 고쳐도 동작을 바꿀 수 있음.
