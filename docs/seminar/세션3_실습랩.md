## 오늘의 주인공 코드 — MemtestG80에서 가장 밀도 높은 15줄

```c
// memtestG80_core.cu:213
__global__ void deviceVerifyConstant(uint* base, uint N, const uint constant, uint* blockErrorCount) {
    extern __shared__ uint threadErrorCount[];          // 블록 공유 버퍼 (512개)
    threadErrorCount[threadIdx.x] = 0;

    for (uint i = 0; i < N; i++)
        threadErrorCount[threadIdx.x] += BITSDIFF(*(THREAD_ADDRESS(base,N,i)), constant);
        //  BITSDIFF(x,y) = __popc((x)^(y))  — 틀린 비트 개수

    for (uint stride = blockDim.x>>1; stride > 0; stride >>= 1) {   // 트리 리덕션
        __syncthreads();                                // ★ 단계마다 동기화 필수
        if (threadIdx.x < stride)
            threadErrorCount[threadIdx.x] += threadErrorCount[threadIdx.x + stride];
    }
    if (threadIdx.x == 0)
        blockErrorCount[blockIdx.x] = threadErrorCount[0];          // 대표 1개만 저장
}
```

3단계 구조:
1. 각 스레드가 자기 word들의 오류 비트 수를 **공유 배열**에 부분합
2. **트리 리덕션**으로 512개를 1개로 접기 (512→256→…→1)
3. 블록당 결과 1개를 전역에 저장 → 호스트가 1024개를 최종 합산

## Exercise 1 — `__syncthreads`를 빼면? (이 세션의 하이라이트)

**① 목표**: 동기화가 없으면 리덕션이 왜 틀리는지 몸으로 배운다.

**② 코드**: `deviceVerifyConstant`(core.cu:227 부근)의 `__syncthreads()`를 **잠깐** 주석 처리합니다.

```c
    for (uint stride = blockDim.x>>1; stride > 0; stride >>= 1) {
        // __syncthreads();                 // Exercise 1: 일부러 제거
        if (threadIdx.x < stride)
            threadErrorCount[threadIdx.x] += threadErrorCount[threadIdx.x + stride];
    }
```

> 같은 리덕션이 `deviceVerifyPairedConstants`, `deviceVerifyWalking32Bit` 등에도 있습니다.
> 이 실습은 `deviceVerifyConstant` **한 곳만** 바꿉니다(Moving Inversions에 영향).

**③ 실행** (여러 번!):
```bash
make -f Makefiles/Makefile.linux64
./memtestG80 128 1
./memtestG80 128 1
./memtestG80 128 1
```

**④ 관찰**: `Moving Inversions` 오류 수가 **실행마다 달라지거나** 0이 아닌 값이 나오나요? (정상 GPU인데도!) 비결정적 결과가 곧 경쟁 조건의 증거입니다.

**⑤ 생각해보기**: 왜 동기화가 없으면 일부 스레드가 "아직 안 써진 값"을 읽게 될까요? 배리어(barrier)의 의미를 자신의 말로 설명해 보세요.

> **반드시 원복**: `__syncthreads()` 주석을 해제하세요. 이 상태로 커밋하면 안 됩니다.

## Exercise 2 — `__popc`는 정말 비트를 세는가

**① 목표**: `BITSDIFF`가 틀린 비트 **개수**를 센다는 것을 확인한다.

**② 코드**: 세션 2 Exercise 2처럼 오류를 주입하되, 이번엔 **여러 비트**를 뒤집습니다.
`gpuMovingInversionsOnesZeros`(core.cu:370)의 첫 write 뒤에:

```c
    SOFTWAIT();
    // === Exercise 2: 3비트 뒤집기 ===
    uint bad = 0xFFFFFF8F;                          // 하위에서 3비트가 0 → 3비트 손상
    cudaMemcpy(base, &bad, sizeof(uint), cudaMemcpyHostToDevice);
    // === 여기까지 ===
    errorCount = gpuVerifyConstant(nBlocks,nThreads,base,N,0xFFFFFFFF,devTempMem,hostTempMem);
```

**③ 실행**:
```bash
make -f Makefiles/Makefile.linux64
./memtestG80 64 1
```

**④ 관찰**: 오류 수가 정확히 **3**인가요? `0xFFFFFF8F ^ 0xFFFFFFFF = 0x00000070` → `__popc = 3`.

**⑤ 생각해보기**: 만약 검증이 "맞다/틀리다"만 셌다면(단순 비교) 이 word의 오류는 몇으로 집계됐을까요? 비트 단위 카운트가 오류율 추정에 왜 더 정밀한가요?

## Exercise 4 — 공유 메모리는 어디서 지정되나

**① 목표**: `extern __shared__` 버퍼의 크기가 커널 launch에서 지정됨을 확인한다.

**② 코드**: `gpuVerifyConstant`(core.cu:198)의 launch 3번째 `<<<>>>` 인자를 봅니다.

```c
    deviceVerifyConstant<<<nBlocks, nThreads, sizeof(uint)*nThreads>>>(base,N,constant,blockErrorCount);
    //                                         ▲ 공유 메모리 바이트 수 = 512 * 4 = 2048 B
```

시험 삼아 이 크기를 **절반**으로 줄여봅니다(의도적 버그).

```c
    deviceVerifyConstant<<<nBlocks, nThreads, sizeof(uint)*(nThreads/2)>>>(...);
```

**③ 실행**:
```bash
make -f Makefiles/Makefile.linux64
./memtestG80 64 1
```

**④ 관찰**: 오류가 폭증하거나 이상한 값이 나오나요? 공유 배열이 부족해 리덕션이 배열 밖을 침범한 결과입니다.

**⑤ 생각해보기**: 삼중 꺾쇠의 세 번째 인자(`<<<grid, block, shmem>>>`)는 무엇을 의미하나요? `extern __shared__`가 크기를 명시하지 않는 이유는?

> **반드시 원복**: 원래 `sizeof(uint)*nThreads`로.

## 마무리 — 자가 점검

- [ ] `extern __shared__`로 블록 공유 버퍼를 만드는 법을 안다.
